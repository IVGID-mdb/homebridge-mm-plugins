# HomeKit reference for bridge plugins

Six topic documents describing how HomeKit models the services a Homebridge-style bridge exposes, and how HAP over IP carries them. Every factual statement in these documents is traceable to one of the two primary sources below, by file and line for the ADK or by page path for Apple; anything that is reasoning rather than source text is marked **INFERRED**, and questions neither source answers are collected in each document's *Open questions* section rather than guessed at.

## The documents

| Document | What it covers |
| --- | --- |
| [accessory-model.md](accessory-model.md) | The structural layer: `Accessory Information` and each of its characteristics, `HAP Protocol Information`, `Service Label` / `Service Label Index`, `Name` vs `ConfiguredName`, primary / hidden / linked service properties, the accessory-category enumeration, aid and iid rules, bridge limits and obligations, and everything `HAPAccessoryValidation` does and does not enforce. |
| [fans.md](fans.md) | The `Fan` service (`0xB7`, debug description `"fanv2"`) and its `Active`, `RotationSpeed`, `RotationDirection`, `SwingMode`, `CurrentFanState`, `TargetFanState` and `LockPhysicalControls` characteristics; what the "Fan v2" naming actually deprecates; and how fan characteristics behave when carried on `Air Purifier`, `Heater Cooler`, `Humidifier Dehumidifier` and `Slat`. |
| [lights-switches.md](lights-switches.md) | `Light Bulb` (On, Brightness, Hue, Saturation, Color Temperature), `Switch`, `Outlet` (Outlet In Use) and `Stateless Programmable Switch` (Programmable Switch Event, which reads as `null` over IP and is exempt from notification coalescing), plus the `Service Label` adjunct multi-button accessories require. |
| [heating.md](heating.md) | `HeaterCooler`, `Thermostat` and `TemperatureSensor`: the two disjoint state families (`CurrentHeaterCoolerState`/`TargetHeaterCoolerState` vs `CurrentHeatingCoolingState`/`TargetHeatingCoolingState`), the threshold setpoints, why every temperature on the wire is Celsius, and how `validValues` restricts a mode picker. |
| [purifier-filter-occupancy-covering.md](purifier-filter-occupancy-covering.md) | `Air Purifier`, `Filter Maintenance` (Filter Change Indication, Filter Life Level, Reset Filter Indication), `Occupancy Sensor` with the generic Status characteristics, and `Window Covering` (position, position state, hold position, obstruction), including the asymmetric Active coupling between a purifier and a linked fan. |
| [protocol.md](protocol.md) | HAP over IP: `GET /accessories`, `GET`/`PUT /characteristics`, `PUT /prepare`; the characteristic-object JSON keys; permission tokens, formats and units; the ten HAP status codes and the handler-error mapping onto them; event subscription, coalescing and delivery; write response, timed writes and authorization data; and the controller-side `HMCharacteristicMetadata` / `HMError` surface. |

Each topic document follows the same shape: per-service characteristic tables (UUID, format, units, min/max/step, valid values, permissions, required/optional, source), then semantics and rules, then the HomeKit framework / Home app view, then implications for a bridge plugin, then open questions. `protocol.md` has no services of its own, so its tables are the wire-level equivalents.

The HAP specification itself is not part of either source, so R14 section numbers appear only as the ADK records them. Apple's pages never publish raw integer values for their enums, so ADK numeric values and Apple case names are matched positionally, and that matching is marked INFERRED where it is used.

Conventions shared across the documents: UUIDs are the Apple-defined short form, expanding to `0000xxxx-0000-1000-8000-0026BB765291`; permission tokens are the strings the IP serializer emits, in order `pr`, `pw`, `ev`, `aa`, `tw`, `wr`, `hd`; where the ADK and Apple disagree (most often an iOS floor of 10.3 vs 10.2), both are recorded and the disagreement is called out rather than resolved.

## How to use this when writing a plugin

1. **Pick the service from the device's real behaviour, not from how you want the tile to look.** Start in the topic document for that family and read the service's required/optional list. A user can re-type a `Switch` or `Outlet` tile through `associatedServiceType` and you are never told — so if the thing genuinely is a light or a fan, publish `Light Bulb` or `Fan`. Remember each *service* becomes its own Home app tile, separately named and roomed.
2. **Copy the characteristic table verbatim into your accessory definition.** Formats are not negotiable: Brightness is `Int`, Hue and Saturation are `Float`, positions are `UInt8`, Color Temperature is `UInt32` mirek. Publish the documented units, minima, maxima and step, narrowed only where the device genuinely cannot reach the full range — controllers build their UI from that metadata and validate writes against it client-side.
3. **Publish every required characteristic, and only the optional ones the device can actually back.** A faked `Brightness`, `Outlet In Use`, `SwingMode` or `CurrentFanState` gives the user a control that lies. Where a required characteristic has no real backing (a `HeaterCooler` with no sensor must still publish `CurrentTemperature`), publish the most honest proxy and keep it stable.
4. **Restrict enumerations with `valid-values`, never by narrowing min/max.** The mechanism is UInt8-only and Apple-defined-type-only — a heat-only device lists `[1]` on `TargetHeaterCoolerState`, a purifier with no auto mode lists `[0]` on `TargetAirPurifierState`. Lists must be strictly ascending.
5. **Match permissions to what you implement, then actually raise events.** `pr` needs a read handler, `pw` a write handler, `ev` a read handler; a controller cannot subscribe to a characteristic without `ev` (`notificationNotSupported`). Nothing raises events for you: every change the controller did not cause — a pull chain, an RF remote, a cloud poll, a setpoint reached — must be pushed, or Home app tiles stay stale forever. Raise only on a real change, and coalesce to no more than one notification per second per connection (Programmable Switch Event is the single exemption).
6. **Get the structure right before the behaviour.** One `Accessory Information` service per exposed accessory with stable Manufacturer/Model/Name/SerialNumber; `aid = 1` for the bridge and a stable unique `aid` for each bridged accessory; `BridgedAccessory` category behind the bridge; at most one primary service per accessory; links only between services on the same accessory; iids stable for the life of the pairing. Changing the set of bridged accessories means bumping the configuration number.
7. **Answer every request, and never fabricate state.** A bridge whose backend is offline is itself still reachable, so it must reply — `-70403` for a transient failure worth retrying, `-70402` for a device that cannot be contacted, and never a blocking handler. Where a service has status characteristics (`Status Active`, `Status Fault`), they are the sanctioned way to say "degraded"; no state enum in these services has an "unknown" member.
8. **Check the Open questions section before inventing a rule.** Home app rendering, N-speed slider detents, filter-level thresholds, occupancy debounce and threshold ordering are all undocumented by both sources. If a decision falls in one of those gaps, it is your policy — make it explicitly and document it in the plugin, rather than assuming HomeKit specifies it.

## Known issues in this set

Two claims in the topic documents conflict with the primary source and with each other; they are listed here so a reader does not act on them before they are corrected.

- **Whether `valid-values` reaches controllers over IP.** `fans.md` states that the IP transport does not serialize valid-values at all, and advises that min/max are therefore the only constraint controllers see. `protocol.md` §1.3 and `heating.md` state the opposite, and the source agrees with them: `GET /accessories` emits `"valid-values"` and `"valid-values-range"` for UInt8 Apple-defined characteristics (`HAP/HAPIPAccessory.c:1516-1525, 1573, 1643`). Only the `GET /characteristics?meta=1` response omits them. Follow `protocol.md` / `heating.md`.
- **Whether declaring both `validValues` and `validValuesRanges` fails validation.** `fans.md` and `heating.md` say it does; the validator at `HAP/HAPAccessoryValidation.c:548-611` checks only that the type is Apple-defined and that each list is correctly ordered, and the IP serializer emits both when both are set. Treat "declare only one" as house style, not as an enforced rule.
